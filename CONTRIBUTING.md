# Contributing to Flood Response API

Thanks for your interest in contributing! This guide covers how to set up the project and the conventions we follow.

## Getting started

No local Go toolchain is required — everything (API, tests, database, migrations) runs inside Docker.

1. **Start the stack**

   ```bash
   make up
   ```

   The API runs on `http://localhost:8080` with Air hot-reload.

2. **Run the checks** before opening a PR:

   ```bash
   make verify
   ```

   `verify` runs `gofmt`, `go build`, `go vet`, and the full test suite. A PR must pass all of these.

## Code style

- Follow `gofmt`. Files must be formatted before submitting — `make verify` fails on any unformatted file in `internal/` or `cmd/`.
- Keep changes focused and reviewable. A PR that mixes unrelated changes is harder to review.
- Match the existing layout (see below).

### Project layout

- `internal/app/<feature>` — feature modules, each with its own DTOs, model, repository, service, handler, and tests
- `internal/pkg/database/migrations` — SQL migrations (managed with Goose)
- `internal/pkg/database/queries` — SQL query definitions (managed with sqlc)
- `internal/pkg/database/sqlcgen` — code generated by sqlc; **never edit by hand**

### Database and sqlc

- Never edit an applied migration. Always add a new one:

  ```bash
  make migrate-create name=<name> sql
  make migrate-up
  ```

- When you change a query in `internal/pkg/database/queries`, regenerate the code:

  ```bash
  make sqlc-generate
  ```

## Testing

- Unit tests live next to the code, using mocks (see existing `*_test.go` files).
- Prefer table-driven tests.
- Changes to behavior must come with tests.

## Commit messages

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
feat: add a new endpoint
fix: correct severity upgrade logic
refactor: extract shared repository helpers
docs: update setup notes
test: cover the matching resolver
```

The scope is optional but useful for larger changes, e.g. `feat(affected-areas): ...`.

## Branching and pull requests

The repository uses two long-lived branches:

- `main` — production-ready. Only promoted from `develop`, never committed to directly.
- `develop` — the development/staging branch where all feature work lands.

Workflow:

1. Create a feature branch off `develop` (e.g. `feature/<name>`).
2. Open a pull request into `develop` when the work is ready.
3. `main` receives changes only by merging `develop` into `main` (a release).

Other rules:

- Keep PRs small; tie each PR to the issue(s) it solves.
- Update the PR description with what changed and why, and any manual verification steps.
- Rebase or merge `develop` into your branch if it drifts; avoid force-pushing shared branches.

## Reporting issues

- **Bugs** — include the request/payload, expected vs. actual behavior, and the API version or commit.
- **Feature requests** — describe the problem you are trying to solve, not just a proposed solution.
- **Security vulnerabilities** — do not report them in a public issue. Email the maintainers directly so the disclosure can be handled privately.
